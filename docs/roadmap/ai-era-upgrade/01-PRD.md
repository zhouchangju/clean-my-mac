# 01 PRD：AI 时代升级

日期：2026-10-14。作者：ZCode（用户口述需求 → 第一性原理评审后成文）。

## 1. 用户原始需求（口述整理）

1. 通读腾讯 lemon-cleaner 开源代码，挑选我们需要的功能并入本软件，特别是
   交互分析方式（如主目录的矩形树图可视化）。
2. 搜索本地磁盘检测/性能监控类 Skill，融合进软件：调用 Skill 做检查、友好
   展示检查结果、对 Skill 扫出的内容提供一键清理/建议；支持自动检测本地
   AI Runtime（Codex CLI、OpenCode 等），可设置默认 Runtime 或选择某个
   Runtime 用 AI 方式做分析和清理。
3. 先产出 PRD、方案文档和细致任务计划，再执行；能并行的用 sub agent 并行。

## 2. 第一性原理审视

### 2.1 还原真实问题

表象需求是"加功能清单"。真实问题是：**一台被 AI 工作流重度使用的 Mac，
其磁盘与内存的占用结构、风险点和清理决策，与传统个人电脑时代显著不同，
而现有工具（包括本软件当前形态）既缺少让人"看懂"占用的交互分析，也缺少
把"专家检查流程"（本地 Skill）和"推理能力"（本地 AI Runtime）组合进产品
的通路。**

### 2.2 必然成立的约束（事实）

- F1 本软件的核心资产是**安全契约**：执行门硬关闭、fail-closed、
  previewOnly 准入、变异测试护栏。任何新功能若绕过这些契约，摧毁的是项目
  存在的理由（自用、可信赖、无遥测）。【代码证据：`Gate.swift`、
  `RuleSet.load` 的 capability 检查、`PERFORMANCE-HANDOFF.md` 明令禁止改门】
- F2 lemon-cleaner 是 GPL（主体 GPLv3、守护进程 GPLv2）。**逐行移植 = 传染
  GPL**。可合法复用的是：公开学术算法（squarified treemap，Bruls 2000）、
  事实性知识（`~/Library/Caches/com.apple.Safari` 是 Safari 缓存这类路径
  事实）、交互模式的思想。实现必须清洁室重写。【证据：仓库 LICENSE.txt】
- F3 本地两个 Guardian Skill 自带强安全协议（迁移双确认 + STOP、内存体检
  45 秒预算 + 校准门 + fail-closed）。App 集成它们时**必须把 App 的 UI 作为
  其协议的确认界面，而不是绕过协议的捷径**；否则"一键清理"会变成对安全
  设计的否定。【证据：两个 SKILL.md 全文】
- F4 本机实际可检测到的 AI Runtime：codex 0.162.1、opencode 1.18.35、
  droid、ollama（claude 未在 PATH）。两者已验证支持非交互执行
  （`codex exec` / `opencode run`）。【2026-10-14 实测】
- F5 Xcode 工程为显式文件引用（非同步组），根包为 SwiftPM；已验证的扩展
  模式是"新功能 = 新 SwiftPM 模块 + App 侧薄胶水"（EXTENSION-PROOF.md）。
- F6 性能验收在途（概览 ≤1% CPU、详情 ≤3%），新功能不得引入常驻开销。

### 2.3 关键假设与检验（苏格拉底式）

- Q「把 lemon 功能都搬进来」到底搬什么？
  反例检验：lemon 的系统级清理需要 root 守护进程（`/Library/Caches`、
  purge、风扇控制）；浏览器隐私清理要改运行中浏览器的 Live SQLite；
  相似照片需要图像解码栈。这些与 F1/F6 冲突或成本收益倒挂。
  → 结论：**只搬用户态、只读可分析、算法可清洁室重写的部分**：
  空间地图交互、重复文件漏斗、大文件类型分类、垃圾规则路径表；
  卸载残留检测与相似照片列为后续阶段（见非目标）。
- Q「Skill 扫出内容一键清理」的"清理"由谁执行？
  若由本 App 执行删除 → 违反 F1。若由 Skill 执行 → Skill 协议本身有
  确认门（F3），App 的角色是**呈现 + 代用户走协议**。
  → 结论：本期"清理动作"限定为两类协议内动作：内存 Guardian 的 green
  候选受控终止（其校准门内）；存储 Guardian 的审计呈现与建议（迁移
  apply/finalize 仍需独立二次确认，本期只到"计划呈现"）。措辞上不再
  使用"一键清理"作为功能名，改为"受控处理"。
- Q AI Runtime 的分析结果可信吗？能执行清理吗？
  AI 可能幻觉出错误路径/错误建议。→ 结论：**AI 只产分析与建议（read-only
  sandbox 执行），其输出永远不直接转化为动作**；用户若采纳，仍走既有的
  计划预览/规则链路。
- Q treemap 已有 top-12 简版，为什么还要 v2？
  现版无下钻/无导航，无法回答"这个大目录里面是什么"——而这是占用分析
  的核心问题。lemon 的答案（下钻 + 面包屑 + 悬停 + 权重压缩）是经过亿级
  用户验证的交互范式。属于"看懂占用"的第一性需求。

### 2.4 对抗性复审（最强反例）

- **反例：范围爆炸。** 5 条产品线 × 安全文化 = 无法在一个迭代内交付。
  缓解：本期全部限定在"只读分析 + 协议受控动作"层，删除执行依然被门挡
  住，因此不引入新的验收债务；每条线有独立开关与独立模块，可部分交付。
- **反例：App 变重破坏性能预算。** 缓解：AI 中心/体检中心/树图/重复扫描
  均为按需触发（无定时器/无轮询/无守护），与 lemon 的 fsevents 常驻监控
  形成刻意对比。
- **隐藏依赖：pbxproj。** 并行子代理同时改 App 工程会冲突。缓解：主会话
  一次性预接线全部新文件与占位页面，子代理只填充自有文件。
- **逆向激励：**"AI 一键清理"是营销话术，不是安全设计。PRD 明确拒绝。
  若未来打开执行门，AI 建议也必须经过与人工选择完全相同的计划/预检链路。
- **缺失证据：** guardian 脚本输出 JSON 的确切 schema 未知（SKILL 未给样例）。
  补救：实施时先实跑采样，解码器做容错 + 人类可读文本兜底显示。

### 2.5 修正后的结论

需求成立，但重述为：**在不动摇安全契约与性能预算的前提下，为本软件补齐
三块 AI 时代的能力拼图——(a) 让人看懂占用的交互分析（树图 v2 / 重复文件 /
大文件分类 / 规则扩充）；(b) 把本地专家 Skill 变成产品内的体检引擎
（协议忠实集成）；(c) 把本地 AI Runtime 变成产品内的分析引擎（检测/选择/
只读调用/建议呈现）。** 删除执行继续保持全局禁用。

## 3. 用户与场景

- 单用户（本机作者本人），中文 UI，完全本地，无遥测。
- 场景 A「磁盘又满了」：打开空间地图 → 逐层下钻找到占用大头 → 大文件/
  重复文件页确认 → 生成建议（规则候选/AI 分析）→ （未来）计划预览。
- 场景 B「AI 工作流卡了/内存紧」：AI 中心 → 内存体检 → 看 Codex 闲置进程
  候选 → 协议确认后受控终止。
- 场景 C「让 AI 帮我看」：AI 中心 → 选择 Runtime → 一键把当前扫描摘要
  （脱敏导出）交给 Codex/OpenCode 只读分析 → 得到中文建议与解释。
- 场景 D「定期体检」：磁盘体检（storage-guardian 审计）→ 迁移候选/
  保留/复查三色分类 → 建议列表。

## 4. 功能需求（本期）

### FR-1 AI 中心（顶层新页面）
- FR-1.1 Runtime 检测：自动扫描 PATH + 常见安装路径，识别
  codex / opencode / droid / ollama / claude 等；显示路径与版本（带超时与
  缓存）；未知/缺失的显示"未检测到"。
- FR-1.2 默认 Runtime：可设置默认（持久化）；执行分析时可临时选择。
- FR-1.3 AI 空间分析：把当前（或最近一次）扫描的脱敏摘要构造为中文分析
  prompt，交给所选 Runtime 非交互执行（codex: `codex exec --sandbox
  read-only`；opencode: `opencode run`）；流式/完成后展示 AI 回答；明确
  标注"AI 输出仅为建议，本应用不会据此执行任何删除"。
- FR-1.4 CLI 对应子命令 `lmc air list|default|analyze`（保持 CLI 与 App
  能力对等的文化）。

### FR-2 体检中心（AI 中心内）
- FR-2.1 Skill 发现：定位 `~/.agents/skills/` 下的 mac-storage-guardian /
  mac-memory-guardian，展示在位/缺失。
- FR-2.2 磁盘体检：运行 `audit.py --output <tmp>`，解析并友好呈现：盘容量、
  实际/表观占用、候选（MIGRATE/KEEP_LOCAL/REVIEW 三色）、读权限盲区；
  生成建议列表。解析失败时兜底显示原始报告文本。
- FR-2.3 内存体检：运行 `guardian_inspect.py run --json`，呈现压力判定与
  候选（green/yellow + 原因 + RSS + 应用名）；执行 Skill 协议的
  calibration-status 检查；压力正常时按协议"报告即停，零动作"。
- FR-2.4 受控动作（严格按 Skill 协议状态机）：
  - green Codex 候选：逐个"终止"按钮（每次动作后重新体检）；
  - calibration_only=true 时：全部提案标注"演示（would do）"，仅提供
    "批准校准"按钮，批准后立即停止，绝不在同轮做任何清理；
  - 45 秒单调预算内运作，超时 fail-closed 报告已完成/已跳过；
  - yellow 应用候选：仅"建议手动退出"提示（v1 协议即 needs-user）。
- FR-2.5 边界文案：明示这些动作由 Skill 协议执行，本 App 不新增删除路径。

### FR-3 空间地图 v2
- FR-3.1 全页 squarified treemap：基于既有扫描索引（mapWeights 去重归因），
  权重对数压缩 + top-N（默认 30）+ 最小权重阈值，小目录也能看见。
- FR-3.2 交互：点击目录瓦片下钻；面包屑直接跳级；前进/后退历史；
  悬停浮层显示名称/大小/占比/修改时间；右键"在 Finder 中显示"；
  瓦片过小时自动隐藏文字标签。
- FR-3.3 头部显示卷容量与可用空间；重扫需确认（与 lemon 行为对齐）。
- FR-3.4 列表模式切换（同层 children 表格，复用既有查询）。

### FR-4 重复文件分析
- FR-4.1 三段漏斗：尺寸精确分桶 → 头 64 KiB SHA-256 分桶 → 组内全量
  SHA-256 确认；默认只扫 ≥1 MiB 普通文件；跳过 `.git` 内部、符号链接。
- FR-4.2 结果按组呈现：每组文件数、单件大小、浪费空间合计；组内可展开
  看路径、在 Finder 显示；页面显示总可去重空间。
- FR-4.3 只读：不提供删除按钮（执行门未开）；提供导出 JSON。
- FR-4.4 进度与取消：字节数进度 + 取消令牌（与既有扫描体验一致）。

### FR-5 大文件分类与规则扩充
- FR-5.1 文件类型分类器：音频/图片/视频/文档/压缩包/安装包/**AI 模型**
  （gguf/safetensors/onnx/mlmodel 等，AI 时代新增类别）。
- FR-5.2 大文件页按类型过滤（复用既有 catalog 查询加分类过滤）。
- FR-5.3 种子规则扩充（全部 previewOnly，事实性路径知识清洁室重写）：
  Xcode DeviceSupport/Archives(review)/CoreSimulator 缓存、Sketch 缓存、
  iPod Photo Cache、iTunes ipsw、Safari/Chrome 缓存、Mail Downloads。
  设备备份目录（MobileSync/Backup）**保持保护**，仅在大文件/洞察中呈现。

## 5. 非目标（本期不做，记录防漂移）

- 任何真实删除/移动执行（执行门保持关闭；M2 未解锁）。
- root 守护进程、系统目录（/Library、/private/var）清理、`purge`、风扇、
  Launchpad 数据库、bpf 网络监控（lemon 需守护进程的部分）。
- 浏览器隐私清理（改运行中浏览器 Live DB，风险与只读姿态冲突）。
- 相似照片、应用卸载残留四策略检测（P2 候选，见 03-TASKS 后续阶段）。
- storage-guardian 迁移的 apply/finalize 执行链（其双确认协议需要专用
  UI 流，本期只做审计呈现 + 建议；计划生成留待后续）。
- ollama/droid 之外的 Runtime 自动安装、登录、配置。

## 6. 验收标准（摘要，细化见 03-TASKS）

- AC-E1 安全不变式：`ExecutionGate.enabled == false`；无任何新增删除系统
  路径调用；全部新规则 previewOnly（加载器强制）。
- AC-E2 并行不变式：概览/详情性能预算不回归（无新增常驻任务/定时器）。
- AC-E3 Runtime 检测在本机实际列出 ≥3 个 Runtime（codex/opencode/ollama
  或 droid），版本显示正确；默认设置重启后保留。
- AC-E4 AI 分析端到端：选择 codex 或 opencode 完成一次真实分析并展示中文
  回答；prompt 上下文来自脱敏导出。
- AC-E5 体检中心端到端：磁盘与内存体检各成功运行一次并渲染结构化结果；
  内存体检在压力正常时零动作退出。
- AC-E6 协议忠实性：内存动作状态机 100% 覆盖 SKILL.md 的 STOP/校准/预算
  规则（单元测试逐条对应）。
- AC-E7 树图可用性：home 扫描后可下钻 ≥3 层、面包屑跳级、前进后退、悬停
  浮层正确；1M 条目索引下首帧 < 1s（按需查询，非全量加载）。
- AC-E8 重复扫描正确性：夹具中已知重复组全部命中、无漏报（跨桶不可能）、
  无假阳性（全量哈希确认）；取消即停。
- AC-E9 分类与规则：分类器边界用例通过；新规则在真实系统路径上命中
  （存在时）且 disposition 合法。
- AC-E10 全量 `swift test` 通过；App Release 构建通过；既有 54 项存储
  测试与 19 项性能测试不回归。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| guardian 脚本输出 schema 未知 | 实跑采样 + 容错解码 + 原文兜底显示 |
| codex/opencode 非交互参数随版本漂移 | 命令构造集中一处 + 版本探测 + 失败给出可复制的手动命令 |
| GPL 污染 | 清洁室：只依据行为描述与公开算法重写；评审时对照检查 |
| 子代理并行改坏共享文件 | 预接线 + 文件所有权划分 + 主会话统一集成验证 |
| 树图大数据量卡顿 | 按需查询当前层（children/mapWeights），仅渲染 top-N |
