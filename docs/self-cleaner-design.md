# 自用 Mac 清理工具：实现依据与设计边界

这是基于逆向结果提出的独立设计，不是对 CleanMyMac 的源码复刻，也不是已实现软件。目标是解释本机空间去向，并在可审阅、可追踪的前提下回收空间。

## 第一版的范围

| 功能 | 第一版行为 | 理由 |
|---|---|---|
| 空间地图 | 选择内置卷/目录，按实际占用排序，显示权限遗漏 | 先找到主要占用，避免只清零碎缓存 |
| 可重建缓存 | 明确规则与版本，展示所属 app、影响、重建代价 | 原程序按应用与知识库分流，不能整段 Library 通删 |
| 开发工具产物 | DerivedData、编译缓存等独立候选，识别活跃任务 | 构建产物可能大，但 Archives、源码和活跃数据库有不同价值 |
| AI 工具缓存 | 精确子路径规则，保留会话、认证、配置、插件和记忆 | 二进制已发现专用规则；自身 AI 历史不应误归类 |
| 大旧文件 | 默认仅审阅；按占用、访问证据和文件类型筛选 | “很久没打开”不等于无价值 |
| 重复文件 | 先发现，逐字节核验，每组保留至少一份 | 文件内容相同不代表物理空间独占 |
| 清理执行 | 明确选择的计划，逐项复核与回执 | 扫描结果会过时；错误必须可见 |
| AI 模型/卸载残留 | 第二阶段；先补共享引用与资源归属验证 | 删除共享 blob 或容器可能破坏仍在使用的资源 |
| 邮件/云文件/备份/系统优化 | 初版不提供自动清理 | 当前没有足够恢复语义与运行证据 |
| app 语言包/架构瘦身 | 初版不实施 | 修改签名 app 的风险与空间收益不匹配 |

上表是功能优先级，不声称已经测得本机各类别的可回收量。

## 建议架构

```mermaid
flowchart LR
  UI[界面：卷与目录选择] --> SC[扫描协调器]
  SC --> FS[文件枚举与属性采集]
  SC --> RU[版本化规则与忽略项]
  FS --> CA[候选与测量状态]
  RU --> CA
  CA --> RV[结果审阅与选择]
  RV --> PL[不可变清理计划]
  PL --> RE[删除前重新核验]
  RE --> EX[执行器]
  EX --> RC[逐项回执与空间复测]
```

原产品观察依据：独立 ScanningCore/CleaningCore/FileManagerService、CMScanResult/CMFileModel、KB ignore 与 helper 边界。上面的组织与命名是自研设计。

实现可先用一个本地 core + CLI 建立可测试行为，UI 再调用同一套接口；技术栈留待开工时选定。原生文件元数据和 macOS 权限边界应由明确的平台适配层承担。

## 最小数据契约

`Rule`：id、version、category、roots、match、exclude、appIdentity、appVersionRange、risk、rebuildCost、defaultSelection、preconditions、actionKind、evidence、enabled。

`Candidate`：id、ruleId/version、displayPath、canonicalPath、volumeId、device/inode、type、mtime、logicalBytes、allocatedBytes、estimatedReclaimableBytes、measurementStatus、ownerApp、reason、selection、lastCheckedAt。

`ScanRun`：id、scope、startedAt、state、progress、processedItems、permissionGaps、errors、cancelled、ruleVersion。未读到的目录单列，不补成 0 字节。

`CleanupPlan`：扫描版本、精确候选 ID 与文件身份、去重后的路径集合、动作类型、风险确认、预计收益、创建时间。父子项重叠只执行一次；规则变更后旧计划失效。

`Receipt`：planId、逐项 precheck/result/error、恢复位置（若有）、动作时间、卷可用空间前后值。成功移动到同卷 Trash 不能宣称已释放空间。

## 规则的准入方式

1. 每条规则写明为什么能重建、何时不能删除、版本适用范围和精确子路径。
2. 根路径不存在、类型不符、活动版本无法解析、匹配范围异常或应用版本未知时，跳过并解释。
3. Protect/Ignore 优先。用户忽略项有路径、应用、类别作用域；不使用无范围的文件名全局匹配。
4. 缓存、日志、临时文件、安装旧版本、离线下载、模型与用户数据分不同风险类。
5. 从 CleanMyMac 观察到的硬编码路径只作为研究线索，先经测试和官方格式核验，才进入执行 allowlist。

例如微信 `Message/MessageTemp` 与整个 `Message` 的风险完全不同；腾讯视频 `Download/video` 可能是主动离线下载，必须显示为离线媒体，而不是默认为垃圾。

## 空间计量

- logicalBytes：文件逻辑长度；allocatedBytes：文件系统分配的空间；estimatedReclaimableBytes：考虑共享、快照等限制后的估计，允许 unknown。
- 以卷为单位，外置盘不并入内置盘收益；符号链接本身与指向内容分开；hardlink 按文件身份去重。
- APFS clone/快照使独占可回收量不一定可精确求得，应标明估计，不能用 apparent size 代替。
- purgeable 是系统估计，与普通缓存候选可能重叠，不直接相加。
- 最终报告空间净变化，但其他进程写入也会影响该值，不把净变化当作每个删除项的精确归因。

## 删除前检查

扫描与删除之间重新核对 volume、device/inode、文件类型、父目录边界与修改状态。路径被替换为 symlink、权限不足、文件正使用或越出允许根目录时，该项失败关闭。仅做字符串规范化不足以解决竞态；底层执行器需要围绕已验证目录身份执行相对操作。

同卷 Trash 提供恢复能力，但通常不立即释放空间。界面应明确区分“已移入废纸篓”和“永久删除并释放”，后者需独立确认。系统目录、挂载点、用户根目录、认证目录、活动数据库不能成为规则的宽泛目标。

## 界面方案

左侧只保留：空间总览、清理候选、大文件与重复项、应用与模型（后续）、操作历史。首页显示当前卷、实际可用空间、最近扫描与覆盖缺口。

结果页左侧分类，中间应用/文件树，右侧解释选中项：为什么入选、来源路径、所属 app、逻辑/占用大小、重建成本、操作方式和忽略按钮。底部只汇总当前明确选择集合，并显示“预计”字样。

用户流程：选择范围 → 扫描及取消 → 结果审阅 → 生成计划 → 复核变化 → 执行 → 逐项回执。可失败、可取消、部分结果可见，不用一个绿色“完成”掩盖跳过项。

## 实现验收案例

| 情况 | 必须看到的结果 |
|---|---|
| 目录无权限 | 扫描 partial，并列出不可访问范围 |
| 扫描中取消 | 保留已发现结果，状态 cancelled；不报告全盘扫描完成 |
| 规则目录变 symlink 或 inode 变化 | 执行拒绝该项，留下明确原因 |
| 父目录和子目录同时选中 | 去重，不重复删除或累加收益 |
| hardlink / APFS clone / sparse file | 逻辑大小与占用/估计分开，未知保留未知 |
| 文件被打开或正在构建 | 跳过/提示，不能伪报成功 |
| 最新备份/离线下载/唯一重复项 | 默认保留，需要明确用户选择 |
| AI 工具当前版本指针无效 | 跳过 stale-version 清理 |
| 两模型共用 blob，只选一个模型 | 不移除仍被引用的 blob |
| Trash 移动成功 | 显示可恢复，不直接增加“已释放”计数 |
| 一项失败、其他成功 | 按项报告，保留失败项再审查 |

这些是下一阶段开发的验收要求，本轮没有实现或执行这些测试。

## 第二轮证据带来的设计补充

- **规则数据与可执行规则分离**：已恢复随包数据库的表与原始记录，但 ScannerID/ItemType、IsRegex 存储类型、GroupType 前缀、规则优先级需要显式转换与校验。不能把数据库行直接解释为删除指令。随包版本也不代表用户运行时更新后的版本。
- **导入保留真实数据类型与异常**：现库 IsRegex 存为文本 `true/false`，不能按非空字符串取布尔值；4 行 ApplicationFiles 缺少可关联的 GroupType，导入应隔离为未解析项。SQLite integrity_check 成功不代表引用关系和执行语义已全部正确。
- **默认选择按类别定义**：普通缓存基类与 Gradle 已有相反策略的实现证据。自研规则应逐项说明默认选择理由，而不是给所有缓存继承同一选择值。
- **备份先按稳定设备身份分组**：最新备份默认保留；两个日期字段都缺失或冲突时，不自动判断“旧备份”。不盲目复制原产品的显示名相关分组策略。元数据不完整也不自动证明备份无恢复价值。
- **模型先形成完整引用图**：缺失或损坏的 manifest 导致 blob 计划不可用；所有引用者均在选择范围内才考虑回收，并在执行前重新核验。GGUF 分片不完整、编号冲突、header 异常要显示原因，不能自动归为垃圾。
- **文件读取失败与内容损坏不同**：实际 plist 谓词区分 open 失败与解析失败；自研应进一步将这些状态显式呈现，并把“损坏”与“可删除”分开。

这些要求基于第二轮静态结果而提出；尚未实现、未通过自研测试，也未证明 CleanMyMac 的所有执行入口均满足它们。
